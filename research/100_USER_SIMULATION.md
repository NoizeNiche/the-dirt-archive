# 100-User Synthetic Usability Pass

## Purpose

This document records a **synthetic 100-session usability simulation** of The Dirt Archive. These are not real people, accounts, analytics, or observed user sessions. Each session is a distinct simulated visitor with a different goal and task path. The value of the exercise is hypothesis generation: finding friction that is plausible across different kinds of visitors, then deciding which product changes are worth testing.

The simulation was run against the current public interaction model: catalog search, dirt-type and builder filters, technical facets, coverage filters, Grid/Table browse modes, Discover, detail pages, saved Workbench records, exact-record comparison, and shareable URLs.

## Cohort

The 100 sessions rotate through 20 visitor archetypes, five sessions per archetype. The archetypes include shoppers, players, collectors, repair technicians, studio users, DIY builders, historians, mobile visitors, beginners, archivists, and link/SEO arrivals.

## Aggregated findings

| Finding | Simulated sessions touching the issue | Product implication |
|---|---:|---|
| Search discovery | 80 | The underlying search is richer than the interface makes obvious. Suggestions reduce guesswork. |
| First-time orientation | 60 | Visitors benefit from a few concrete jobs-to-be-done instead of only archive description. |
| Comparison pruning | 60 | Comparison should support easy removal of one record without resetting the set. |
| Zero-result recovery | 40 | A dead end should contain the obvious next action. |
| Keyboard search flow | 40 | Search suggestions should be fully operable without a mouse. |
| Workbench state visibility | 20 | Saved and compare state should be legible from the launcher itself. |
| Photo coverage context | 20 | Coverage gaps should read as archival state, not broken functionality. |
| Share context | 20 | Shared views need obvious context at arrival. |

## What the simulation says to preserve

The simulated visitors consistently benefit from the archive's core model: **Search → Dirt Type → Builder → Pedal**. The descriptive comparison model is also useful because it lets visitors put exact records side by side without introducing a popularity or recommendation layer.

The simulation does **not** justify adding ratings, rankings, social popularity, seller mechanics, or inferred circuit claims. Those would change the character of the archive rather than simply make it easier to use.

## Changes made from this pass

The first implementation batch addresses the highest-frequency friction points:

1. Search now exposes a suggestion popover with matching records and the reason each record matched.
2. Search suggestions support ArrowUp/ArrowDown, Enter, and Escape.
3. Zero-result states now provide a direct recovery action.
4. Workbench launcher state can show saved and compare counts together.
5. Comparison headers now include a per-record Remove action.
6. The comparison link button now reads the current comparison state when clicked instead of relying on an older captured selection.

## Interpretation

The strongest recurring opportunity is not "add more features." It is **make the existing archive's depth discoverable**. A 4,000+ record catalog has a large search space, so visitors need small cues that reveal what they can do without turning the interface into a dashboard.

The next product layer worth investigating is a guided **pedal identification workflow**: let a visitor narrow an unknown pedal by builder clues, dirt family, documented technical facts, version family, and photos, while explicitly stopping short of guessing an exact identity when the evidence is insufficient. That would serve repair techs, collectors, historians, and curious players without compromising the archive's descriptive model.
